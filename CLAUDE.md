0\. Главный принцип
Сначала понять и согласовать — потом писать код. При любой развилке в бизнес-логике
остановись и спроси, не угадывай. Неверно угаданное бизнес-правило = быстро сгенерированный
мусор, откат которого дороже одного вопроса.

1\. Режим работы (всегда)
Сначала анализ и план — без правок кода.
Показываешь план, я подтверждаю.
Только после явного «погнали / делай шаг N» — реализация.
Ведёшь живой TODO по ходу; в конце — отчёт, что именно изменено.

2\. Когда ОБЯЗАТЕЛЬНО остановиться и спросить
Развилка в бизнес-логике — ВСЕГДА стоп + вопрос. Если есть два разумных толкования
правила, поведения, «как должно быть» — не выбирай молча.
Любое необратимое/рискованное действие: миграции, удаление данных, массовые правки,
изменение .proto-контрактов, новые зависимости.
Неоднозначное требование или недостающий контекст.
Что вопроса НЕ требует (делай и продолжай): локальные технические решения внутри уже
согласованного плана, имена, форматирование, очевидные обратимые правки.

3\. Как спрашивать
По-русски, пронумерованные варианты решений (2–4), у каждого — короткий trade-off.
Один вопрос = одна развилка. Не сваливай несколько решений в один вопрос.
Дай свою рекомендацию, но дождись моего выбора, прежде чем действовать.

4\. База данных — read-only по prod
По умолчанию только SELECT. Никаких INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER и миграций
по боевой БД без отдельного явного разрешения на конкретное действие.
У тебя нет прямого доступа к БД: формулируй SQL, отдавай мне — я верну результат.
Делай выводы по факту, а не по догадке.
SQL: идемпотентный, с LIMIT, читаемый, с комментарием «зачем этот запрос».
Любую гипотезу о данных сперва проверь запросом, потом строй на ней вывод.

5\. Не ломай
Минимальный diff. Не трогай несвязанный код, не рефактори «попутно».
Сохраняй текущее поведение, если явно не просили его менять.
.proto — контракт между backend и frontend. Не меняй wire-совместимость без
согласования: на той стороне сломается клиент.
Не добавляй зависимости без разрешения.
Не трогай секреты и .env, не печатай их значения. Различай prod / staging / local.
Не доверяй памяти: сверяйся с реальной схемой (Prisma), реальным кодом, реальными данными.

6\. Тесты
Тестовое окружение изолировано от prod. Тесты не мутируют боевую БД.
Сначала — read-only / consistency тесты: SELECT-проверки инвариантов текущей базы.
Контракты сторонних API проверяй отдельно, без записи в БД.
Не подгоняй тест под баг — фиксируй ожидаемое поведение.

7\. Definition of Done
Что сделано и что изменено (список файлов), как это проверить.
Какие допущения сделаны и где они могут оказаться неверными.
Что осталось, какие риски.

8\. Анти-паттерны (стоп-слова для самопроверки перед ответом)
Выдумал бизнес-правило вместо вопроса.
Чиню симптом, а не корень.
Молча расширил scope задачи.
Изменил .proto / схему / prod-данные без разрешения.
Строю вывод на догадке о данных вместо SELECT.
Доверяю памяти о коде вместо чтения файла.
Сроишь плохую, не оптимизированную архитектуру, файлы более 400 строк
